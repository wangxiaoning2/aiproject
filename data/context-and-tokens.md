# 上下文、token 与成本

## 模型本身没有记忆

你看到的"它记得前面说过什么"，其实是每次请求都把整个对话历史重新发了一遍。服务端不保存任何会话状态，状态全在客户端手里——这也是为什么刷新页面之后它就"忘了"。

## token 怎么估

中文一个字大约 1 个 token，英文 4 个字符大约 1 个 token。这个估算不精确，但足够用来做预算控制。真正精确的用量要看接口返回的 usage 字段，很多兼容端点默认不返回流式的用量，得额外打开开关。

## 上下文窗口满了怎么办

最朴素的策略是从最新的一条往前保留，超出预算的老消息直接丢掉。更细的做法有几种：把早期对话摘要压缩成一段话；只保留和当前问题相关的历史轮次；把长期需要记住的信息落到向量库里，需要的时候再检索出来。

要注意的一条坑：失败的回答不能塞回上下文，否则模型会以为自己真的说过那些话，后面会顺着这个错觉继续编。

## 账单失控的大头在输入端

对话到第二十轮的时候，输入 token 会远远超过输出，因为每一轮都要把全部历史重新算一遍。所以省钱的重点在输入端：控制历史长度、压缩重复的系统提示词、把检索到的资料裁剪到只留最相关的几段。很多人第一次看到月度账单被吓到，原因基本都是历史无节制地累积。

## 首 token 延迟才是用户真正感知到的

总耗时很长但首字很快就出来，用户感觉是"流畅"；总耗时不算长但前几秒毫无反应，用户就觉得"卡死了"。所以做产品时优先优化的是首 token 延迟，而不是总时长。
