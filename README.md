# ai-week1-streaming

手写 SSE 的流式对话 demo。**零运行时依赖**，不装任何库，也没有构建步骤。

目的只有一个：让"大模型流式输出"从黑盒变成你能逐行读懂的东西。跑通它，你就跨过了第 1 周最大的那道坎——把 AI 从"好神奇"降级成"一个慢一点、按流返回、可能中途挂掉的接口"。

---

## 跑起来（两条命令）

```bash
cd ai-week1-streaming
node server.ts
```

打开 http://localhost:5173 就能用。没配 API Key 会自动进 **mock 模式**——本地伪造流式输出，不花钱，但走的链路和真实模型一模一样。

想看真实模型，就这样：

```bash
cp .env.example .env
# 编辑 .env，填上 LLM_API_KEY，LLM_BASE_URL 换成你要用的服务商
node --env-file=.env server.ts
```

任何 OpenAI 兼容端点都能接：DeepSeek、通义、智谱、Kimi、本地 Ollama 都行。

## 五个必须搞懂的机制

这五个就是这个 demo 的全部内容，也是第 1 周任务清单上的五件事。

### 1. 为什么不能直接调模型，要自己写一个 Node 代理？

因为 **API Key 不能出现在浏览器里**。一旦写进前端 JS，任何人打开 DevTools 就能拿走你的额度。

所以浏览器 → 你的服务端 → 模型服务商。中间这一层代理顺便帮你做了三件事：藏密钥、裁剪上下文、把成本算出来。

### 2. SSE 到底长什么样

它就是一段**纯文本**，通过一条不关闭的 HTTP 连接持续推过来。格式简单到离谱：

```
event: token
data: {"t":"你"}

event: token
data: {"t":"好"}

event: done
data: {"usage":{...}}
```

规则只有三条：

- 一行 `event:` 声明事件名
- 一行或多行 `data:` 承载数据
- **一个空行表示这一帧结束**

服务端按这个格式写（见 `server.ts` 的 `sse()` 函数），前端按这个格式读。就这么简单。

> 为什么不用 `EventSource`？因为它只能发 GET，没法带 JSON body、没法自定义请求头。所以真实项目里几乎都是 `fetch` + `ReadableStream` 自己手动解析——就是 `public/app.js` 里 `handleFrame` 干的事。

### 3. 流式解析最容易踩的坑：chunk ≠ 一帧

这是写流式最容易翻车的地方。

你 `await reader.read()` 拿到的 `chunk`，**不代表一条完整的 SSE 消息**。TCP 只是字节流，服务端一次写入的内容可能被拆成两个 chunk 送过来，变成这样：

```
第一次 read():  "event: token\ndata: {\"t\":\"你"
第二次 read():  "好\"}\n\n"
```

如果你假设 chunk 等于一帧，就会在某些请求里随机丢字——而且只在网络抖动时出现，极难复现。

正确做法就一句：**自己维护 buffer，累积解码后的字符串，按空行切分，剩下的留在 buffer 里等下一轮**。

`public/app.js` 里那段 `buffer += decoder.decode(value, { stream: true })` 就是干这个的。注意 `{ stream: true }` 不能省——中文一个字占 3 个字节，正好被切在两半的时候，不加这个参数会解出乱码。

### 4. 用户点"停止"，钱该什么时候停

很多人以为前端不渲染就是停止生成了。不是的。

前端停止读流，**服务端和模型之间的请求还在跑**，token 还在烧钱，账单照记。你必须让这件事传到上游去：

- 前端：`AbortController.abort()`
- 服务端：监听 `res.on('close')`，一收到就 `controller.abort()` 掐掉上游的 fetch

`server.ts` 里这段是有意写给你看的：

```ts
res.on("close", () => {
  if (!controller.signal.aborted) {
    controller.abort();
    console.log(`[abort] 客户端断开，已取消上游请求`);
  }
});
```

试一下：**回答到一半点停止生成，然后看终端日志**。

### 5. 上下文不是无限的，也不是免费的

模型本身没有记忆。你看到的"它记得前面说过什么"，其实是每次请求都把整个对话历史重新发一遍。

这带来两个必须处理的问题：

- **上下文窗口会满。** `server.ts` 里的 `trimContext()` 是最朴素的策略：从最新往前保留，超预算的老消息直接丢。生产环境会做得更细——摘要压缩、只保留相关轮次、把长期信息落到向量库。
- **每次都要为全部历史付费。** 对话到第 20 轮的时候，输入 token 会远超输出。所以成本优化的大头在输入端，不在输出端。

顺带理解一下 `estimateTokens()`：中文一个字大约 1 token，英文 4 个字符大约 1 token。这个估算不精确，但足够用来做预算控制。

## 三个动手练习（照着做一遍，比读十篇文章管用）

**练习一 · 打开"原始 SSE 报文"面板**
发一句话，然后盯着那个面板看。你会发现所谓"AI 打字"，本质就是一堆小 JSON 拼在一起，一个 token 一个 `data:` 帧。黑盒感在这一刻就消失了。

**练习二 · 发「测试报错」**
mock 模式里埋了一个故障开关：收到这句会在流到一半时抛错。观察前端怎么处理——自动重试一次，第二次还失败才把错误暴露给用户。然后回答自己一个问题：**为什么失败的回答不能塞进上下文？**（因为那样模型会以为自己真的说过那些话。）

**练习三 · 压低 MAX_CONTEXT_TOKENS**
`.env` 里把它改成 `200`，重启，然后连着聊几轮。看右侧"上下文条数"面板里 `（−N）` 是怎么涨起来的——那是被裁掉的消息数。你就直观地看到了"上下文预算"这件事。

几处值得反复看的代码：

| 位置 | 看什么 |
|---|---|
| `server.ts` → `sse()` | 一个 SSE 帧怎么组装 |

## 已知限制

这是教学项目，不是生产代码。缺的东西：没有鉴权、没有限流、没有并发控制、没有真正的持久化、上下文裁剪策略很粗糙、日志只打到终端。

生产环境还需要：请求队列与并发上限、按用户的额度控制、SSE 的断线重连与断点续传、敏感词与内容安全、全链路追踪。

——这些缺口本身就是你后面几周要补上的东西，也是面试里可以主动聊的加分点。
